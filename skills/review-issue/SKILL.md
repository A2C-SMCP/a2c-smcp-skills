# Review Issue — 开工前 Issue 审查

依次回答三个问题：

1. **内容是否最新**：Issue 中待定的决策，现在是否已经明确？
2. **任务是否成立**：协议变更、前置 Issue、对称 SDK 镜像 Issue 的实际交付，是否改变了本任务的前提、范围或验收标准？
3. **是否值得投入**：这个问题是否值得通过改动解决，以及是否值得现在解决？

Issue 写于过去，实施发生在现在。按过时的描述开工，会让实施者反复查询已定的决策，或者交付一个前提已经失效的任务。问题存在、代码可以改进、已经有人建了 Issue，都不能单独证明投入合理；也不要为减少改动而忽视实际损失。允许结论是接受现状。

## 与 issue-radar 的分工

| Skill | 回答 | 粒度 |
|-------|------|------|
| `issue-radar` | 这件事是否已经有人在别处做、方案会不会撞车（看得到**未建立关联**的 PR、Discussion、对称仓 Issue） | 广度，每批一次 |
| `review-issue`（本 Skill） | 这个 Issue 本身是否最新、成立、值得现在做（只沿**已建立的关联**取证） | 深度，每个 Issue 一次 |

派活前先跑 `issue-radar`；被判定「已有人推进 / 方案冲突」的 Issue 不再审查，直接走合并、协调或升级 protocol-owner。

## 输入与边界

接受 Issue 链接或 `<仓库>#<N>`、Review 发现、优化或重构建议、问题描述。没有 Issue 的输入跳过 Step 1–2。批量输入时逐项给出结论，共享同一根因或收益的事项合并权衡，避免重复计算价值。

**GitHub 取证清单**——GitHub 没有 Jira 式 issuelinks，前置与关联关系散落在 timeline 与 task list 里，必须显式读取，不能只看 body：

```bash
R=A2C-SMCP/<仓库名>; N=<编号>
gh issue view $N -R $R --json number,title,body,state,author,labels,milestone,createdAt,updatedAt,comments
gh api repos/$R/issues/$N/timeline --paginate \
  --jq '.[] | select(.event=="cross-referenced" or .event=="connected" or .event=="referenced" or .event=="milestoned" or .event=="closed") | {event, created_at, source: .source.issue.html_url, commit: .commit_id}'
gh api repos/$R/issues/$N/sub_issues --jq '.[] | {number, title, state}'            # 子任务
gh api repos/$R/issues/$N --jq '.parent // empty'                                      # 父任务（若平台返回）
gh pr list -R $R --search "$N in:body" --state all --json number,title,state,mergedAt # 关联 PR
```

body 中的 task list（`- [ ] #M`）、「blocked by / mirror of / 协议依据」引用，以及 timeline 中的 cross-reference 共同构成关联集。协议依据还要核对协议仓 develop 上对应规范与向量的**当前**内容（`git -C <协议仓> show origin/develop:<路径>`），而不是 Issue 创建时的描述。

- **唯一的写操作**：经用户逐项确认后，按 Step 1 写回规则更新**当前 Issue**（预检模式下不写）。不建单、不关单、不改 Milestone、不改其他 Issue、不改代码。
- 发现其他 Issue 也受影响时，列出受影响 Issue 与原因，建议用户随后在对应仓库处理，本 Skill 不代写。
- 工具或权限不足时说明未能核实的内容，只问会改变结论的问题，不把取不到证据写成「没有问题」。
- 本 Skill 不替代 `add-feature` / `fix-issue` 的门控（协议归属、Milestone、镜像）；审查结论不自动启动这些流程。

取证需要大范围检索代码、历史或关联 Issue 时，交给 Explore 等只读子代理并行收集，只回收结论与证据位置。

## 预检模式

调用方（如 sdk-architect 派活前）在隔离子代理 `issue-reviewer` 中以 `--precheck` 运行本 Skill：完整执行 Step 1–6 的取证与判断，但**不提问、不写回**。无法当场核实的事项标为待用户确认，不自行拍板。只返回以下报告：

```text
Issue：<仓库>#<N>    主结论：<建议改动 / 暂缓改动 / 先验证 / 接受现状>
可否按原样分配：<是 / 否（原因）>
写回清单（未写入）：<原文片段 → 替换内容 → 依据>
任务成立性：<判定> — 原前提 → 变化（证据链接）→ 影响 → 可选处理与推荐
契约与对称：<协议依据是否仍有效、是否已合协议 develop；镜像 Issue 及其状态；相关向量>
待用户确认：<会改变结论的未知或需要用户裁决的取舍>
受影响的其他任务：<仓库#N — 原因>
```

调用方只传 Issue 链接、契约锚相关条款与架构约束，**不传自己对方案的倾向**；预检收到倾向时忽略它，从零取证。

## 1. 回填已明确的待定决策

扫描 body 中的待定内容：「待定 / TBD / 待确认 / 待协议裁决 / 方案 A 或 B / 等 X 完成后再定」，以及以未完成前置为条件的假设。

按以下来源寻找结论：Issue 评论 → 父 Issue / tracking Issue → 协议仓 Discussion 裁决（`answer-ask` 留痕处）→ 关联 Issue 与 PR 的**实际交付**（已合并代码、已发布版本，而不是原计划）→ 协议仓 develop 的规范与向量 → 当前代码。区分提议、后续决定和实际交付；来源冲突时以有可核实证据的最新明确决定为准。

- **已明确**：列入写回清单。
- **仍未明确或证据冲突**：保留原文，列为关键未知；会影响后续结论时向用户提问。不凭推断填写。
- **决策改变了范围或验收标准**：不当作文本替换，转入 Step 2 一并商定。

写回清单逐项给出：原文片段、替换内容、依据（链接、决策人、日期）。用 `AskUserQuestion` 请用户确认，可逐项接受或拒绝。写回规则：

| 场景 | 写法 |
|------|------|
| 内部作者 + 小片段待定项 | 原位替换，替换处注明来源，如 `（已定：<Discussion 链接>，2026-10-23）`；不追加到末尾，不重写无关段落，保留原作者结构与措辞 |
| 范围或验收标准变更 | 原位更新后，**另留一条一句话评论**：「按 <决策链接> 调整范围/验收：<一句话>」——GitHub body 编辑只有 edited 标记，评论让时间线与 watcher 看得到 |
| 外部作者 / 社区 Issue | **不改 body**；用评论写决策与依据，请作者或维护者更新 |
| 决策来源是 Discussion / PR | body 里只放结论 + 链接，不复制讨论过程 |

写入用 `gh issue edit <N> -R <repo> --body-file <file>`：先读完整原文，只替换已确认片段；写入后读回核对表格、代码块、task list、链接格式没有丢失。

## 2. 识别前置变化，判断任务是否仍成立

先写出本任务依赖的前提：协议规范与向量（章节、字段、错误码）、前置 Issue 提供的能力、对称 SDK 镜像 Issue 的方案、Milestone 目标、范围边界、验收标准。再对照现状：

- 协议依据在协议 develop 上是否已改（字段改名、语义调整、向量增改）、是否已发布。
- 前置、父级、子任务、镜像 Issue 的**实际交付**是否偏离原计划：接口改名、能力合并、范围缩减、方案更换、提前完成了本任务的部分内容。
- 对称 SDK 是否已按另一种方案实现了同一行为（触发 core-governance §2 管辖判定）。
- 当前代码是否仍符合 Issue 描述的起点。

逐项判定：

| 判定 | 含义 |
|---|---|
| 仍成立 | 前提未变，按原描述推进 |
| 需调整 | 目标仍有效，但范围、方案起点或验收标准需要修改 |
| 已被覆盖 | 部分或全部内容已由其他 Issue / PR 交付 |
| 前提失效 | 协议或前置变化使本任务的目标不再需要或不再可行 |
| 被阻塞 | 依赖的协议变更或前置 Issue 尚未就绪（协议未合 develop 即被阻塞，core-governance §4.3） |
| 归属错位 | 本仓 Issue 实为协议辖区（core-governance §2）——转协议先行，本仓改为跟进 Issue |

「仍成立」以外的每一项，都向用户讲清：原前提 → 发生了什么变化（附证据链接）→ 对本任务的具体影响 → 可选处理（按原样做、调整后做、合并、废弃、等待前置、转协议先行）及各自代价 → 推荐哪一个、为什么。用 `AskUserQuestion` 商定，允许多轮；达成一致前不静默改范围，也不按旧描述开工。商定的范围或验收调整按 Step 1 写回。

## 3. 核实问题与当前基线

基于更新后的 Issue，把输入还原成一句话：谁在什么场景下遇到什么后果，希望改善什么可观察结果。把报告者提出的解决方案与问题分开。

- 当前代码入口与调用链是否支持该问题；Issue 指向的路径是否仍活跃。
- 现象与协议规范、一致性向量、验收标准有何差距；是否属于合理限制、误用、已解决的问题或已有能力可覆盖的场景。
- 测试、一致性对拍结果、日志、用户反馈与近期变更能证明什么，是否存在相反证据。
- 对称 SDK 在同一点上的行为——不一致本身就是证据，但先判定是谁偏离了规范。

明确标记事实、推断和未知。问题已经解决时，说明证据及是否仍有残留影响。

## 4. 比较收益、成本与风险

选择与决策相关的共同时间窗口（如本 Milestone、下一个 X.Y），比较：

| 维度 | 要回答的问题 |
|---|---|
| 实际影响 | 影响谁（SDK 消费者、Computer 用户、对端互操作）、多少场景、频率与严重程度？有哪些绕过方式？ |
| 改动收益 | 降低什么损失、解除什么阻塞、消除什么跨 SDK 不一致？收益能否归因于本次改动？ |
| 完整成本 | 设计、开发、评审、回归、**镜像到对称 SDK 的成本**、协议变更与版本升级、迁移、维护 |
| 改动风险 | 是否改变 wire 行为或兼容性、是否破坏已发布版本、影响面与可回退性 |
| 不改或推迟 | 不一致是否扩大、是否错过本 X.Y 的发版窗口、保留现状是否让后续更容易 |
| 机会成本 | 挤占本 Milestone 哪些已知更重要任务？缺排期信息就标未知 |

能量化时给出来源、区间与假设；收益与成本用相同窗口。不编造用户规模、事故概率、工时或精确 ROI，不以任意加权评分代替判断。

### 判断纪律

- 「更优雅」「最佳实践」「以后可能需要」、重复代码、缺少某种抽象，只是调查线索；说明它们如何造成实际损失或阻碍已确认的目标。
- **「对称 SDK 有、本仓没有」不自动等于该做**：无消费方的能力不对称可以暂缓；造成 wire 不兼容或对端可感差异的不对称必须处理，且协议先行。
- 不要求一定等到事故发生才改；可达的互操作故障路径、明确的协议 MUST 条款可以支持预防性投入。
- 高严重性也要核实受影响路径；不能因报告写了「协议违规」就直接认可——先确认规范原文确实如此要求。
- 同时寻找改与不改的反证，避免为原建议背书，也避免机械地反对。

## 5. 比较合适的处理路径

始终把接受现状或推迟作为基线，再比较适用路径：补测试或向量、文档澄清、协议裁决、配置或使用方式调整、复用已有能力、针对性修复、系统性改造。问题值得解决，不代表输入中建议的方案值得采用。

审查深度与决策影响匹配：先获取最可能改变结论的证据；额外调查已不会改变结论时停止。需要实验时只提出能区分决策分支的最小方案、判据与停止条件。

## 6. 给出结论与改变结论的条件

| 主结论 | 适用条件 | 必须交代 |
|---|---|---|
| **建议改动** | 收益或风险降低足以支持投入，关键成本风险已能判断 | 推荐路径、为什么现在值得做、主要风险及验证目标（含须通过的向量） |
| **暂缓改动** | 问题成立，但时机、依赖或优先级不支持（含协议未合 develop、前置未就绪） | 延期代价、重新评估的具体事件或阈值；不能只写「以后再说」 |
| **先验证** | 存在会实质改变投入决定的关键未知 | 最小取证或实验、判据与各结果对应的结论 |
| **接受现状** | 证据支持不改，问题已解决或被覆盖，或前提已失效 | 接受的限制或剩余风险，以及什么变化会使改动值得做 |

只选一个主结论。写不出该结论的「必须交代」项，就不算完成。缺少关键证据时不要包装成确定的拒绝；关键未知已不影响当前决定时，也不要用「先验证」逃避判断。

先给结论，再给依据；复杂问题使用：

```text
主结论与推荐处理路径：
时间建议与证据把握：
Issue 内容更新（已回填 / 待确认 / 仍未明确）：
前置变化与任务是否成立（含与用户商定的结果）：
契约与对称（协议依据、镜像 Issue、向量）：
问题、当前基线与实际后果：
收益、完整成本和改动风险（共同时间窗口）：
不改或推迟的代价：
备选路径与取舍依据：
关键未知、反证及会改变结论的条件：
受影响的其他任务：
下一步最小行动：
```

证据尽量链接到代码位置、Issue、PR、Discussion 或测试，并注明适用版本或观察时间。不得将建议写成已执行结果，不自动把「接受现状」变成关闭 Issue，把「建议改动」变成创建 Issue。

需要校准判断或给用户解释时，按需读取 [SMCP 正反案例](references/examples.md)。案例都是假设场景，不能用关键词套用。
