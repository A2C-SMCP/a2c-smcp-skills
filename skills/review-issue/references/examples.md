# SMCP Issue 审查正反案例

以下都是假设场景，用于说明证据如何改变结论，不代表任何仓库的实际状态或固定决策阈值。每对案例表面症状相同、证据不同、结论相反——用来对抗关键词套用。

## 1. 同样是规范歧义，结论可以相反

**场景 A**：规范对「未传 `timeout` 时的默认超时」只写了「SHOULD 有合理默认」。python-sdk 默认 30s、rust-sdk 默认 60s，Agent 侧观察到同一工具在两端超时表现不同，已有用户反馈重试策略失效。

- 主结论：**建议改动**，路径为**协议先行**。
- 理由：默认值出现在对端可感行为中（protocol-scope「出现在报文中的默认值」），两 SDK 各执一词即属协议管辖；不能在任一 SDK 单边改成另一方的值。
- 下一步：协议仓明确默认值并补向量；两 SDK 跟进 Issue 挂同 X.Y，blocked-by 协议变更合入 develop。

**场景 B**：规范对某字段的描述措辞模糊，但两 SDK 的实现都满足现有规范的任一合理解读，wire 结果一致，对端无法观察到差异。

- 主结论：**接受现状**（实现层面），附带低成本的文档澄清建议。
- 取舍：没有互操作后果，不值得动实现；把澄清作为协议文档改进单独评估，不阻塞本 Issue。
- 改变结论的条件：出现第三方实现或新场景使两种解读产生可观察差异。

## 2. 同样是双 SDK 不对称，结论可以相反

**场景 A**：rust-sdk 有一个便捷构造器，python-sdk 没有；没有消费方依赖它，也不影响 wire 行为。Issue 要求 python 补齐「以保持一比一」。

- 主结论：**暂缓改动**。
- 取舍：SDK 公开 API 形态属 SDK 自治（protocol-scope）；core-governance §3 的「一比一」约束的是共享实现策略，不是每个便捷方法。无消费方时补齐只增加维护面。
- 重新评估条件：出现跨语言示例、文档或消费方需要对等 API。

**场景 B**：rust-sdk 对某错误码的 details 结构多带一个字段，python-sdk 不带；Agent 侧按 rust 的形态解析，接 python Computer 时解析失败。

- 主结论：**建议改动**，且**归属错位**——这是协议辖区。
- 理由：差异体现在报文结构上；先判定谁偏离了规范（`git grep` 协议 develop），规范没定义该字段则协议先行补定义与向量，偏离方再跟进。
- 不做的事：不在 python 侧直接「补上 rust 的字段」——那会让现有实现倒逼规范。

## 3. 同样是测试缺口，结论可以相反

**场景 A**：某场景向量要求「真实传输 + 不挂起」，SDK 的测试全部用合成异常或进程内 mock transport，没有任何用例在真实 server 上断言错误码且有 time-box；历史上同类路径曾在生产中挂起至超时。

- 主结论：**建议改动**。
- 理由：规范 MUST 条款可达但未被守护；合成异常会把「库吸收错误后挂起」这类真实失效盖住（conformance-tests §2.0 测试学硬条款），已有事故史说明这不是理论风险。
- 下一步：恢复真实 server 用例，每景同一用例内断言 expected 全部字段 + time-box。

**场景 B**：同一向量，SDK 已在真实传输上逐景断言错误码与不挂起；`isError` 形状由共享结果构造器的单元测试覆盖，传输级用例只断言错误码。

- 主结论：**接受现状**（在当前规则口径下）。
- 取舍：构造器是唯一出口，单测已锁定形状；为每景再加传输级断言收益很小。
- 改变结论的条件：治理规则明确要求「场景向量每景传输级断言全部字段」，或出现绕过共享构造器的新出口。

## 4. 同样是向量变更，版本处理可以相反

**场景 A**：修正某数据向量的算法细节（如名称规范化规则），已有 SDK 版本发布并据旧规则生成了持久化标识。

- 主结论：**建议改动**，但必须随契约版本升级与迁移说明发布。
- 理由：已发布包与落库数据依赖旧结果，原地修订会让同一 X.Y 下出现两种结果。

**场景 B**：同样的修正，但该向量只在协议 develop 上新增、尚未随任何 X.Y 发布，SDK 也只在 develop 分支对拍。

- 主结论：**建议改动**，在当前进行中的 X.Y 内修订即可。
- 取舍：无已发布依赖，无需升版；两 SDK 重新同步副本即可。

## 5. 同样是「同主题已有工作」，结论可以相反

**场景 A**：本仓 Issue 要求实现某能力；对称 SDK 的已合并 PR 连带把协议仓向量与规范也补齐了，本仓剩余工作只是同步副本与对拍。

- 主结论：**需调整**后建议改动——范围缩到「同步向量 + 对拍 + 实现差异部分」，写回 body 并留一句话评论。

**场景 B**：两个仓库各有一个标题相近的 Issue，但一个处理握手阶段的授权失败、一个处理工具调用阶段，规范分属不同章节、不同错误路径。

- 主结论：两者都**仍成立**，不合并。
- 取舍：不能因标题相近就判「已被覆盖」；按规范章节与错误路径区分。

## 6. 待定决策已有结论，回填 body 再开工

**证据**：Issue 写着「默认 Room 命名待协议裁决」。协议仓 Discussion 已有 protocol-owner 的管辖裁决与结论，协议 PR 已合入 develop。

- 处理：写回清单列出原文、替换内容与依据（Discussion 链接、裁决日期、协议 PR），用户确认后原位替换为结论 +「（已定：<链接>，日期）」。
- 不做的事：不把被否决的备选方案细节写进 body。
- 若结论只出现在跨 Session 消息里、没有落到 Discussion：**不算已定**，保留「待定」并列为关键未知——消息只是传输层。

## 校准边界

- 案例不决定是否建单；「接受现状」不是永久否决；「暂缓」必须带重新评估条件。
- 案例中的版本号、字段与数值都是虚构的，不要当作当前规范引用。
