# Clarify — oasp-protocol 专属指南

> 通用流程参见 SKILL.md 主文件。

## 项目上下文

- **类型**：Office AddIn Socket Protocol 规范
- **工具链**：MkDocs 文档站点、Markdown 规范文件
- **定位**：定义 office4ai（MCP Server）与 office-editor4ai（Office 加载项）之间的 Socket.IO 通信协议

## 影响视角定义

OASP 协议影响链条：协议变更 → office4ai + office-editor4ai 双端适配 → AI 操作 Office 的行为变化 → 终端用户体感。使用**定制二视角**：

| 视角 | 本项目中的含义 |
|------|---------------|
| **协议实现者** | office4ai（Server 端）和 office-editor4ai（Add-In 端）的开发者——协议变更需要双端协调实现 |
| **协议消费者** | 任何基于 OASP 协议构建自定义 Office 集成的第三方开发者 |

## 关键用户画像

### 画像 1：双端实现者
- 场景：OASP 协议新增事件类型或修改字段，需要在 office4ai 和 office-editor4ai 两端同步实现
- 敏感点：协议一致性（两端的序列化/反序列化是否完全对齐）、错误处理语义
- 典型问题：「协议把 `document.connected` 事件加了 `client_info` 字段，但 Add-In 端还在用旧版本——新字段为 null 时 Server 端应该怎么处理？」

### 画像 2：第三方集成者
- 场景：基于 OASP 协议构建自己的 Office 工具集成
- 敏感点：协议文档的完整性和清晰度、向后兼容策略
- 典型问题：「OASP 的 `error` 事件有两种格式——文档里只写了新版，我该怎么兼容旧版 Add-In？」

## 协议特有影响维度

| 维度 | 追问 |
|------|------|
| 双端同步 | 这个协议变更要求 office4ai 和 office-editor4ai 同时上线还是可以分批？不分批的话中间态会有什么问题？ |
| 版本协商 | Add-In 版本和 Server 版本不一致时，协议能否协商降级？ |
| 错误语义 | 协议错误码的定义是否足够精确——两端实现者会不会各自解读出不同行为？ |

## 典型决策场景

| 场景 | 核心影响维度 |
|------|-------------|
| 新增事件/字段 | 双端实现同步成本 + 旧版 Add-In 兼容 |
| 事件命名/格式改版 | 协议消费者迁移 + 双端实现对齐 |
| 错误处理规范修订 | 协议一致性——错误行为在各端的表现 |
