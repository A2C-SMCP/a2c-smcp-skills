# Clarify — a2c-smcp-protocol 专属指南

> 通用流程参见 SKILL.md 主文件。

## 项目上下文

- **类型**：SMCP 协议规范文档
- **工具链**：MkDocs 文档站点、Markdown 规范文件
- **定位**：A2C-SMCP 体系的总规范——定义 Agent-Server-Computer 之间的协议契约。所有 SDK 实现（python-sdk / rust-sdk）都必须遵守

## 影响视角定义

协议项目没有传统「终端用户」——影响链条是：协议规范变更 → SDK 实现适配 → 开发者使用新特性/行为 → 最终用户体验变化。因此使用**定制二视角**：

| 视角 | 本项目中的含义 |
|------|---------------|
| **SDK 实现者** | python-sdk 和 rust-sdk 的维护者——他们必须按协议规范实现行为，协议变更直接转化为代码适配成本 |
| **生态参与者** | 所有使用 SMCP 协议的外部项目和开发者——协议定义了他们的集成方式和互操作边界 |

> 视角 3（SDK 消费者）在本项目中表现为「协议消费者」——任何实现 SMCP 协议的第三方。

## 关键用户画像

### 画像 1：SDK 实现者（python-sdk / rust-sdk 维护者）
- 场景：协议规范变更后，需要在各自 SDK 中实现对应行为
- 敏感点：变更的明确程度（模糊定义 → 两 SDK 实现不同 → 互操作 bug）、向后兼容性、过渡期
- 典型问题：「协议把 `client:tool_call` 的 `timeout` 字段从可选变必填——两个 SDK 都要改，还要协调上线顺序」

### 画像 2：协议消费者（第三方实现者）
- 场景：基于 SMCP 协议构建自己的 Agent/Server/Computer
- 敏感点：协议清晰度（如果规范有歧义，实现会跑偏）、变更频率、迁移指南
- 典型问题：「协议 v2 改了事件命名规范，我现有的 v1 实现还能和官方 Server 通信吗？」

## 协议特有的影响维度

| 维度 | 追问 |
|------|------|
| 双实现一致性 | 这个协议变更是否容易在 python-sdk 和 rust-sdk 中做出一致实现？模糊点在哪？ |
| 向下兼容 | 旧版 SDK 的客户端/Server 能否和新版互通？过渡期多长？ |
| 规范清晰度 | 新规范是否有歧义空间？两个独立实现者会读出不同语义吗？ |
| 时序依赖 | 协议变更需要「先更新哪边、后更新哪边」？不同步会出什么问题？ |

## 典型决策场景

| 场景 | 核心影响维度 |
|------|-------------|
| 协议字段增删改 | SDK 实现者适配成本 + 向下兼容策略 |
| 事件命名/语义重新定义 | 双实现一致性 + 协议消费者迁移 |
| 新增协议能力（如新事件类型） | SDK 实现者工作量和优先级的权衡 |
| 协议版本演进策略 | 全生态影响——所有实现者和消费者 |
