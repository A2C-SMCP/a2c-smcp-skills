# Clarify — 技术决策体感翻译

把技术讨论从「每个词都认识，但不知道实际意味着什么」翻译成你可以感知的影响——你的用户会怎么体验这个变化？你的开发者同事需要改什么？外部 SDK 消费者会被影响吗？

核心价值：用**用户场景、交互步骤、等待秒数、改动文件数、迁移成本**等可感知指标，替代技术术语堆叠。

---

## Step 0：收集输入

### 0.1 输入形态分派

| 输入 | 处理 |
|------|------|
| **Jira Issue 链接**（`*.atlassian.net/browse/*`） | 用 `mcp__atlassian__getJiraIssue` 拉取标题、描述、评论 |
| **Jira Issue Key**（如 `PROJ-123`） | 先查当前项目关联的 cloud，再用 `mcp__atlassian__getJiraIssue` 拉取 |
| **GitHub Issue/PR/Discussion 链接** | 用 `gh issue view` / `gh pr view` / `gh api` 拉取标题、正文、前 20 条评论 |
| **文本片段**（用户粘贴） | 直接使用 |
| **留空**（无链接无文本） | 从当前会话上下文中提取最近讨论的技术决策点 |

### 0.2 上下文确认

如果从上下文推断话题，先用**一句话**向用户确认「你要澄清的是不是：xxx？」再继续。不要猜错方向浪费篇幅。

---

## Step 1：确定项目上下文与影响视角

根据当前工作目录判定项目，加载对应资源文件获取该项目的**影响视角定义**和**关键用户画像**：

> 各项目资源：`{baseDir}/resources/<project>.md`

资源文件告诉你：该项目有哪些用户类型、每个视角该问什么问题、典型决策场景是什么。

**如果不在任何已知项目中**：使用通用三视角（见 Step 3），并在分析中标注「缺少项目特定用户画像，分析基于通用假设」。

---

## Step 2：提取技术决策点

从输入中提取所有**需要做选择/判断的技术点**：

1. **方案选项**：讨论中涉及哪些选项？（Option A / B / C ...）
2. **争议焦点**：不同参与者在争论什么？（性能？复杂度？兼容性？）
3. **隐含假设**：讨论中被默认的前提是什么？（「用户肯定需要 X」「这个接口不会变了」等）

**如果只有一个方案、没有显式对比选项**：把「做 vs 不做」「现在做 vs 以后做」作为默认对比维度。

**如果讨论的是一个已决定的方向、只想理解影响**：跳过对比，直接进入 Step 3 做单方案影响分析。

---

## Step 3：多视角影响分析

对每个选项，逐一通过以下视角分析实际影响。**每个技术点必须落到「谁在什么场景下会感觉到什么变化」。**

### 视角 1：终端用户 — 他们能感受到什么？

| 分析维度 | 追问 |
|----------|------|
| 交互变化 | 操作步骤变多还是变少？多几步？等待/确认/切换有增减吗？ |
| 功能体感 | 以前不能做什么、现在能做了？以前能做的、现在还一样吗？ |
| 错误体验 | 出问题时用户看到什么？提示信息是更好懂还是更费解？ |
| 性能体感 | 操作响应变快还是变慢？量化到「秒」级别——用户能感觉到吗？ |

### 视角 2：开发者 — 他们需要做什么？

| 分析维度 | 追问 |
|----------|------|
| 接口适配 | API 签名变了吗？需要改多少处调用？有自动迁移脚本吗？ |
| 心智模型 | 概念是变简单还是变复杂？需要学新框架/新概念吗？ |
| 调试体验 | 出问题时更好定位还是更难？日志/错误信息有改善吗？ |
| 维护成本 | 以后改相关功能是更容易还是更困难？代码量增减？ |

### 视角 3：SDK / 外部消费者 — 生态影响

| 分析维度 | 追问 |
|----------|------|
| 兼容性 | 现有消费者的代码会被 break 吗？有弃用过渡期吗？ |
| 学习曲线 | 新用户上手更容易还是更难？文档/示例需要跟着重写吗？ |
| 生态方向 | 这个选择让生态更开放（多实现互操作）还是更封闭（与单一实现绑定）？ |

> **SDK / 协议项目必答视角 3**。非 SDK 项目可跳过或替换为该项目的「外部集成方」视角。具体见各项目 resource 的「影响视角定义」。

### 分析纪律

- **禁止用技术术语解释技术术语**：不说「引入了一个 Thunk 层」，说「调用方不需要改代码，但首次调用会多等约 50ms」
- **量化到可感知的数字**：步骤数、秒数、需改动的文件/调用数、代码行数增减
- **不确定时标注**：如果某项影响无法从当前信息判断，标注「待确认」而不是猜测

## Step 4：对比与建议

### 4.1 影响矩阵

用 ✅/⚠️/❌ 直观标注各选项在三视角下的表现：

```
| 视角 | Option A | Option B |
|------|----------|----------|
| 终端用户 | ✅ 操作从 5 步变 3 步 | ⚠️ 无变化 |
| 开发者 | ⚠️ 需改 12 处调用 | ✅ 零改动 |
| SDK 消费者 | ✅ 向后兼容 | ❌ 破坏性变更，需 6 个月过渡 |
```

### 4.2 给出建议

给出明确推荐 + 理由。如果有**「短期痛但长期值」**的选项，显式标注：

- **忍耐成本**（开发和用户要忍什么、忍多久）
- **收益兑现时间线**（什么时候能看到好处）

**如果你无法判断用户更看重哪个视角**（如「快速上线」vs「长期架构」），用 AskUserQuestion 确认优先级后再给建议，而不是自行假设。

## Step 5：输出格式

```markdown
## 要澄清的技术话题
[一句话概括]

## 方案概述
- Option A: [一句话]
- Option B: [一句话]

## 体感影响分析

### Option A
- **你的用户会感受到**：...
- **你的开发者需要做**：...
- **SDK 消费者受影响**：...（如适用）

### Option B
- **你的用户会感受到**：...
- **你的开发者需要做**：...
- **SDK 消费者受影响**：...（如适用）

## 对比矩阵
[Step 4.1 表格]

## 建议
[推荐 + 理由 + 短期痛长期值选项的代价与收益时间线]

## 需要你确认的假设
[分析中依赖但不确定的假设，列出来让用户纠正或确认]
```

## 反模式

| 反模式 | 正确做法 |
|--------|---------|
| 复述技术细节而不翻译成体感 | 每个技术点必须落到「谁在什么场景下会感觉到什么变化」 |
| 只分析一个选项 | 至少对比「做 vs 不做」两个方向 |
| 忽略用户优先级 | 不确定哪个视角更重要时，用 AskUserQuestion 确认 |
| 用技术术语解释技术术语 | 用操作步骤数、等待秒数、需改动文件数等可感知指标 |
| 跳过隐含假设 | 显式列出分析依赖的假设，让用户有机会纠正 |
| 所有项目用同一套分析维度 | SDK 项目必含 SDK 消费者视角；加载项目 resource 获取定制视角 |
| 不确定的影响瞎猜 | 标注「待确认——需要更多信息才能判断」 |
| 长篇技术分析淹没了对比结论 | 对比矩阵和推荐必须在开头 30 秒阅读量内可见 |
